> - 检索：`2026-09-24-fulltext-search-at-scale.md`

## 1. 业务定位

**服务对象**：法学院的朋友，以及他们接入 MCP 的 AI。

**核心价值**：让引用可以核对。具体是三件事：

1. 条文原文准确；
2. 效力状态准确；
3. 能按案件发生时间取到当时有效的版本。

AI 本身擅长“从案情想到大概哪条”，但经常背错原文、引用旧版本、编造条文。数据库负责
弥补这一侧。

**检索需求的排序**：

| 需求 | 重要性 | 对应工作 |
| --- | --- | --- |
| 查已知条文、核对原文 | 最高 | 法规名解析、全量数据 |
| 按案件时间取版本、判断效力 | 最高 | 版本链、废止日期、`as_of` |
| 研究某个用语（精确、完整、可过滤） | 高 | 全量下的精确检索、排序、过滤 |
| 记得大意、原文措辞对不上 | 中 | 最小限度的模糊检索 |
| 从学理概念或案情找条文 | 低（由 AI 负责） | 只给落空提示 |

## 2. 做什么

### P0：数据正确

**A. 法规作品与版本**（仓库内）

- `laws` 增加 `work_id`，以 flk 的历史沿革 `lsyg` 归组。
- `as_of` 改为跨记录选版本，修复民事诉讼法 2017 版在库、却按日期取不到的问题。
- 效力状态按日期推算：同一作品内，某个版本适用到下一个版本施行的前一天。
- 废止关系和废止日期写入 `law_relations`。
- 查询时点早于最早版本时，明确返回“无可用版本”，不用现行版本顶替。

**B. 全量导入与每日对账**（仓库外的维护脚本）

- 首次导入：
  - flk 只取详情，约 3.1 万次请求，间隔 3 秒，约 26 小时；
  - 原文从 lawtext 镜像取得，抽样比对哈希；
  - 切条、归组，抽取废止关系；
  - 生成 JSON，用 `sync --from-dir` 装入新库。
- 每日对账：拉取全部列表（31 次请求），只处理有变化的记录。
- 仓库配合：`sync --from-dir` 支持大批量装载；JSON 增加 `work_id`、
  `status_checked_at`。

### P1：精确检索在全量数据下可用

- **条文索引改为二元组**：精确检索的语义不变，但 2 字查询不再退回 LIKE 全表扫描，
  索引体积也更小。这是为了让精确检索撑得住全量数据，不是为了模糊检索。
- **排序**：按层级排，法律、司法解释、行政法规在前，地方性法规降权；现行版本在前。
- **过滤**：`level`、`status`、`region`、`as_of`。
- **历史版本默认折叠**，结果数量准确。
- **引用识别**：在检索框里输入“民法典第五百零四条”，直接返回该条。
- **远端 MCP**：`chinalaw_search` 增加 `as_of`；开放 `chinalaw_applicable`。

### P2：最小限度的模糊检索

- 精确检索为 0 条或不足时，追加“各片段都出现在同一条文中、不要求连续”的结果，
  按相关度排序，逐条标为近似。需求里两个 0 命中的例子属于这一类。
- 法规名解析失败时返回候选，不自动采用，例如“个保法”“电商法”。
- 完全落空时提示 AI 改用法条原文用语重新检索。

### P3：收集使用证据

- 服务端记录检索请求：查询词、参数、命中数、耗时。私域规范的查询不记录正文。
- 目的：用真实查询决定后续是否做更多的模糊检索。**需要事先告知使用者。**

### 顺手修正

- skill 中“一般部门规章走 flk”的指引是错的，flk 没有部门规章。

## 3. 不做什么

| 项目 | 原因 |
| --- | --- |
| 语义向量检索 | 已决定搁置 |
| 错别字提示 | 收益小；AI 调用方很少打错字 |
| 学理术语表 | 由 AI 负责；等 P3 的证据再议 |
| 部门规章接入 | flk 没有；来源调研已留档 |
| 状态对账做成 CLI 功能 | 属于维护者的数据生产工作，放在仓库外 |
| 早期版本补齐 | 不在首次导入范围；以后按重要法律清单逐步补 |
| 独立搜索引擎、向量数据库 | 单文件 SQLite 足够 |

## 4. 部署调整

- **新服务器**：腾讯云国内服务器，并为域名办理 ICP 备案。甲骨文服务器只做试验。
- **影响**：
  - 国内服务器访问 flk 的路径更直接，被 WAF 挡住的概率较低。首次导入和每日对账
    建议直接在这台服务器上跑。
  - 备案期间，域名不能对外提供网页服务，但服务器可以先跑导入。
  - 全量库约 1.1–1.5GB，原始 docx 缓存约 1–2GB，2 核 4G 加 40GB 以上的磁盘够用。
    检索延迟要在这台机器上重新实测。
  - 新服务器从空库开始，由全量导入建库。甲骨文上如果有手工录入的数据（私域规范等），
    需要导出备份后迁移。现在无法登录甲骨文，要等登录恢复后再确认。

## 5. 实施顺序

| 步骤 | 内容 | 在哪里做 | 前置条件 |
| --- | --- | --- | --- |
| 1 | 顺手修正 skill；P3 检索日志 | 仓库 | 无 |
| 2 | P0-A 法规作品与版本，用现有 fixture 测试 | 仓库 | 无 |
| 3 | P0-B 导入脚本，先在本机对全国层级（约 2,500 条）试跑，验证归组、切条、废止关系 | 仓库外 | 2 |
| 4 | P1 精确检索的全量改造 | 仓库 | 2；用第 3 步的数据验收 |
| 5 | P2 最小模糊检索 | 仓库 | 4 |
| 6 | 腾讯云服务器上跑全量导入，部署，配置每日对账 | 服务器 | 3、4；可先于备案完成 |
| 7 | 备案完成后开放域名，各 agent 切换到新地址 | 服务器 | 备案 |

步骤 1、2 可以立即开始，不依赖服务器。
