# flk 全量导入方案（草案）

> 状态：草案，待确认。日期 2026-09-25。本文只讨论数据如何进库和保持更新；检索
> 怎么用这些数据，见 `2026-09-24-fulltext-search-at-scale.md`。
> 文中“实测”均指 2026-09-24 至 25 对 flk 接口的只读探测，总计约 30 次请求，间隔
> 不少于 3 秒。

## 0. 结论

- **定位**：导入和对账都是**维护者的数据生产工作**，不是使用者的功能。它们应该做成
  仓库之外的维护脚本。仓库只负责三件事：
  - 数据格式：沿用 `sync --from-dir` 的 JSON，补几个字段；
  - 装载：一次装入全量数据，以及逐部法规的增量更新；
  - 查询时按日期推算效力状态。
- 对账不是一次性的：首次导入是一次性的，之后每天要做一次增量对账。两者都放在仓库外。
- **版本归组可以直接用 flk 官方的“历史沿革”**（详情接口的 `lsyg` 字段），不必按标题
  猜。只有更名的法规、废止日期和 flk 缺失的早期版本需要另外处理。
- **flk 的历史版本不完整**，这会直接限制“按案件时间检索”的能力范围，必须对使用者
  讲明，见第 3.3 节。
- 首次导入对 flk 约 3.1 万次请求，只取详情。原文 docx 从开源镜像
  lawtext/legal-data-docx 批量获取，不再逐个向 flk 下载。按 3 秒间隔约 26 小时，
  可以断点续跑，分三个晚上跑完。
- 开源数据集都没有可靠的版本链；效力状态只有直接取自 flk 的那几份可信（附录 B）。

## 1. 定位：数据生产与数据使用分开

| | 数据生产（维护者） | 数据使用（服务） |
| --- | --- | --- |
| 做什么 | 抓取 flk、清洗切条、归组版本、提取废止关系、每日对账 | 检索、按条号取条文、按日期选版本、推算当日效力状态 |
| 谁来运行 | 你，在服务器或本机上 | 法学院的朋友，通过远端 MCP 或面板使用 |
| 放在哪里 | 仓库之外的维护脚本目录（例如私有仓库 `chinalaw-ops`） | chinalaw 仓库 |
| 对外依赖 | flk 接口；可选的第三方数据集 | 无网络依赖 |

这样划分的理由：

- 服务可能不开源，也只有一个维护者。把抓取、对账逻辑做成通用 CLI 功能，就要照顾
  “每个使用者都自己抓 flk”的场景：配置、报错、文档、测试都要按公开发布的标准来做，
  还会把 flk 的访问压力放大到每个安装实例。放在仓库外，只需满足你自己的运行环境。
- 仓库里现有的 `fetch`、`sync --incremental` 继续保留，供开源用户按需补单部法规。
  它们与全量流水线互不依赖。
- 两边的接口是“法规数据 JSON”（CONTRACT §7）。维护脚本产出 JSON，服务端用
  `sync --from-dir` 装载。以后换数据来源，服务端不受影响。

仓库需要配合的改动（属于检索方案中的 1a 步骤）：

1. JSON 与 `laws` 表增加 `work_id`、`status_checked_at` 两个字段；
2. 版本关系、废止关系写入现有的 `law_relations` 表（`relation_type` 已有 `replaces`、
   `amended_by` 等取值，目前是空表）；
3. `sync --from-dir` 支持大批量装载：分批提交事务，装载完成后统一重建检索索引。

## 2. flk 数据实测

### 2.1 规模与分类

| 时效性 `sxx` | 条数 | 最早公布日期 |
| --- | ---: | --- |
| 3 有效 | 17,222 | 1950 |
| 2 已修改 | 8,112 | 1951 |
| 1 已废止 | 3,209 | 1953 |
| 4 尚未生效 | 82 | 2026-03 |
| 空（修改、废止的决定等） | 约 2,270 | — |
| 合计 | 30,896 | |

分类树（`enumData` 接口）：宪法；法律（法律、法律解释、有关法律问题和重大问题的
决定、修正案、修改废止的决定）；行政法规（行政法规、修改废止的决定）；监察法规；
地方法规（地方法规、法规性决定、修改废止的决定）；司法解释（高法、高检、联合发布、
修改废止的决定）。**没有部门规章。**

### 2.2 每类接口提供什么

| 接口 | 关键字段 | 用途 |
| --- | --- | --- |
| 列表 `search/list` | `bbbs`、标题、`gbrq` 公布日期、`sxrq` 施行日期、`sxx` 时效性、`flxz` 性质、制定机关 | `pageSize=1000` 可用，31 次请求取完全部记录；也是每日对账的数据来源 |
| 详情 `flfgDetails` | 以上字段，另有 `lsyg` 历史沿革、`ossFile` 原文路径（docx、pdf、ofd）、`content` 章节条目录树、`xgzl` 相关资料（如主席令） | 版本归组；获取原文；核对切条数量 |
| 下载 | docx 原文 | 条文正文的来源 |

### 2.3 历史沿革（`lsyg`）能解决什么

实测样例：

| 法规 | `lsyg` 返回的版本 |
| --- | --- |
| 公司法 | 2023、2018、2013，三个 `bbbs` |
| 民事诉讼法 | 2023、2021、2017 |
| 反间谍法 | 2023、2014 |

同一链条上的记录互相列出，对这些链条求并集（union-find）即可得到法规作品。这比
上一版方案里“标题相同 + 制定机关相同”的规则更可靠，归组规则改为：

1. **以 `lsyg` 为准**；
2. `lsyg` 为空、标题和制定机关都相同的记录，作为候选合并，写入待审清单，由人确认；
3. 更名的法规由人工维护映射表。例如反间谍法 2014 的前身是国家安全法 1993，`lsyg`
   不跨更名；国家安全法 2015 是另一部新法，`lsyg` 为空。

## 3. flk 缺什么

### 3.1 没有废止日期

合同法在 flk 上标为“已废止”，但详情中没有废止日期，没有指向民法典的关系，`lsyg`、
`xgzl` 都为空。

按案件时间取版本时，需要知道“合同法哪天起不再适用”。废止日期的来源，按可靠程度
排列：

1. **“修改、废止的决定”**：flk 上的独立记录，有自己的施行日期，正文列出被废止的法规
   名称。可以解析出“被废止的法规 → 废止施行日期”。
2. **新法附则中的“同时废止”条款**：例如民法典第一千二百六十条“……《中华人民共和国
   合同法》……同时废止”。全量正文到手后，可以用规则批量抽取。
3. **仓库现有的 `data/applicability/` 规则文件**（6 份，人工整理）。
4. 以上都没有：`repealed_at` 留空，但记录“最早观察到已废止的日期”作为上限。查询时
   对这类法规附带提示。

1、2 两项的抽取结果，全国层级（约 3,000 条已废止记录中的全国部分）要人工抽检。地方
性法规按规则抽取，不做人工复核。

### 3.2 部分记录缺字段

例如劳动合同法实施条例的 `sxrq`（施行日期）为空。缺施行日期的记录，按公布日期推算，
并标注 `effective_at_inferred`。导入时统计缺失数量，数量大时再定规则。

### 3.3 早期版本不全

| 法规 | flk 收录的版本 | 实际的修订史 |
| --- | --- | --- |
| 公司法 | 2013、2018、2023 | 还有 1993、1999、2004、2005 |
| 民事诉讼法 | 2017、2021、2023 | 还有 1991、2007、2012 |
| 刑法 | 2009、2020 两个合并文本 | 仓库 fixture 自行维护了 16 个版本 |

后果：案件发生在 flk 最早版本之前时，无法给出当时的条文。处理原则：

- 这类查询必须返回“该时点无可用版本”，不能拿现行版本顶替。现有的
  `version_not_found_as_of` 已经是这个行为，要保证全量数据下仍然如此。
- 仓库出厂 fixture 里已有的历史版本（刑法 16 版、宪法各版、民事诉讼法、公司法等）
  优先于 flk，合并进对应的法规作品。
- 需要更早版本的重要法律，可以从全国人大常委会公报、中国人大网补齐。这项工作量要
  逐部评估，不在首次导入范围内。

## 4. 首次导入流水线（仓库外脚本）

```
A 列表快照 ─► B 详情 ─► C 原文 ─► D 清洗切条 ─► E 关系构建 ─► F 装载 ─► G 验收
```

| 阶段 | 内容 | 请求数 | 说明 |
| --- | --- | ---: | --- |
| A | 分页拉取全部列表，保存快照 | 31 | 也是之后每日对账的比较基准 |
| B | 逐条请求详情，保存 `lsyg`、`ossFile`、目录树 | 约 3.1 万 | |
| C | 获取 docx 原文：先从开源镜像 lawtext/legal-data-docx 批量取得，按 `bbbs` 对应，从 GitHub 下载，不占 flk 请求；镜像缺失的再向 flk 下载 | 镜像缺失的部分，预计数百 | 抽样 1–2% 向 flk 重新下载并比对文件哈希，确认镜像可信；扫描件或缺原文的记录单独列清单 |
| D | 用现有的 `cleaning.parse_articles_from_docx` 切条 | 0 | 用详情里目录树的“条”节点数核对切条结果，不一致的进入人工清单 |
| E | 按 `lsyg` 归组；解析废止决定和“同时废止”条款；合并仓库 fixture | 0 | 产出 `work_id` 和 `law_relations` |
| F | 生成 JSON，`sync --from-dir` 装入一个新的库文件，建检索索引 | 0 | 不直接写正在服务的库 |
| G | 统计、抽样、跑评测集 | 0 | 通过后才替换 |

**访问节奏**：串行请求，间隔 3 秒，保留 chinalaw-cli 的 User-Agent。遇到 WAF 挑战页或
非 200 响应就停止并记录断点，下次从断点继续。按北京时间夜间运行，约需 26 小时，
分三个晚上完成。

**原始文件的保存**：docx 约 3 万个，放在维护脚本的缓存目录，不进服务端的库和备份包，
因此不受备份包“最多 2 万个文件”的限制。原始文件是重建数据的依据，建议另外做一份
冷备份。

**第三方数据的作用**：

- lawtext/legal-data-docx 只作原文的下载缓存。它是 flk 原始 docx 的逐日镜像，文件按
  `bbbs` 命名，并附文件哈希。仓库没有声明许可证；法规文本本身不受著作权保护（著作权法
  第五条），作缓存风险低，但不转发这个数据包本身。
- senry5433 数据集（CC0）的条文表用来交叉核对我们的切条结果。
- 任何第三方数据都不作为效力状态、日期或版本关系的来源。

## 5. 持续更新：每日对账（仓库外脚本）

每天北京时间凌晨运行一次：

1. 拉取全部列表（31 次请求，约 2–3 分钟），与上一次的快照比较；
2. **新增记录**：请求详情、下载原文、切条，按 `lsyg` 挂到已有作品上，或建立新作品；
3. **`sxx` 或日期变化**：更新状态字段，写入变更日志；
4. **新出现的修改、废止决定**：解析出被废止的法规和施行日期，写入 `law_relations`；
5. **记录从列表中消失**：只告警，不删除；
6. 所有记录更新 `status_checked_at`，产出增量 JSON，由服务端 `sync --from-dir` 逐部
   装载。

施行日到来时的状态切换，不依赖这个脚本：服务端按日期推算（检索方案第 6.3 节）。
对账脚本的作用是发现事先无法预知的变化，并核对 flk 与本地推算是否一致。

服务端展示 `status_checked_at`。对账连续多日失败时，面板和 `doctor` 显示警告。

## 6. 装载与替换

两种方式，建议首次导入用 A，日常更新用 B：

- **A 整库替换**：维护脚本生成一个全新的库文件，验收通过后替换服务端的库文件。风险
  是面板里手工录入的数据（私域规范、人工修正）会被覆盖。**替换前必须把这部分数据
  迁移过去**，具体做法取决于第 9 节问题 3 的答复。
- **B 逐部增量**：对单部法规做 upsert，每部法规一个事务，检索索引同步更新。面板数据
  不受影响。

## 7. 部门规章：现在的 fetch 是怎么做的

- **没有专门的部门规章数据源。** `data/source_coverage.json` 中的国家规章库（`gjgzk`）
  状态为 `planned`，没有实现。
- 现在能取到部门规章的只有三个入口，都是“一次取一部”的 `fetch`，都不支持批量
  `sync`：
  - `csrc_gov_cn`：证监会令；
  - `nfra_gov_cn`：金融监管总局、原银保监会有稳定编号的规章；
  - `gov_xzfgk`：主业是国务院行政法规库。它另外写死了 3 个 gov.cn 静态页面（商业
    银行股权管理暂行办法等），也接受 `gov_cn:content_<编号>` 形式的 id 去取任意
    gov.cn 正文页，页面栏目是“部门规章”时标为部门规章。前提是调用方事先知道页面
    编号。
- **skill 里的指引是错的**：`chinalaw-fetching` 的来源表写着“一般部门规章 → flk_npc，
  flk 含部分部门规章”。实测 flk 的分类树里没有部门规章，agent 按这条指引只会得到
  0 命中。这个问题与导入无关，可以先单独修正文档。

部门规章的来源调研见检索方案附录 A。结论不变：本轮不接入。

## 9. 待确认的问题

1. **维护脚本放在哪里**：建议新建私有仓库 `chinalaw-ops`，放导入、对账脚本和运行
   记录。还是放在服务器的某个目录下即可？
2. **首次导入的做法**：flk 只取详情，3 秒间隔，约 26 小时，分三个晚上跑完；原文用
   开源镜像，抽样比对哈希后使用。是否接受？
3. **现有库里手工维护的数据**：远端库里目前有哪些手工录入的内容（私域规范、人工修正
   的别名等）？这决定首次导入能否直接整库替换。
4. **废止日期的人工抽检**：全国层级的废止关系自动抽取后，人工抽检的比例定多少？
   建议全国层级 100% 过一遍列表（约几百条），地方性法规不抽检。
5. **早期版本补齐**：是否列一份“重要法律早期版本”清单，逐步补齐？例如公司法、民事
   诉讼法、刑事诉讼法、民法通则时代的主要民商事法律。

## 附录 A：实测记录

- 列表接口 `pageSize` 为 1000 时单次约 1–1.6 秒、415KB；为 100 时约 0.8 秒、39KB。
- 列表接口的 `sxrq` 区间过滤参数无效（返回的总数不变），按 `sxrq` 排序有效。
- 响应头带 `WZWS-RAY`，说明前面有网站卫士 WAF。全部探测请求都正常返回 200，但有
  一次返回了非 JSON 内容，约一分钟后恢复。原因不明，可能是 WAF 的挑战页。
- 本机经 Clash 代理访问时，flk 域名解析到 198.18.x.x 的假 IP，现有 CLI 的网络策略
  会以“非公网地址”为由拒绝请求（`netio.py:122`）。服务器上没有这个问题；本机跑维护
  脚本时要让 flk 绕过代理的假 IP 模式。
