# 降低企业部署资源需求：进行中的验证

目标：继续降低每次请求的 CPU、内存与固定 I/O 开销；用户明确选择以 **2 核、2GB 内存下的稳定多人并发** 为主验收目标，同时保留更低配置对照。不能只用重复查询或查询层峰值代替真实服务验证。

基线是已上线的 `2e2d26b`（schema 17）。本轮在 `codex/low-resource-search` 分支和隔离数据副本上工作，未替换线上程序，也未改变线上并发限制。

## 当前候选改动

1. 无须正文过滤的 FTS 搜索先排序窄候选行，再读取入选正文。需要逐条检查、法规或章节过滤时仍在 LIMIT 前完成过滤，不改变候选数量和评分公式。
2. 令牌仍逐次查询有效性、权限和撤销状态，但同一秒的相同 `last_used_at` 不重复写入，保持原有秒级精度。
3. 服务生命周期内使用一个串行查询日志写连接，WAL + synchronous FULL、每条事务提交；不关闭审计，不采用可能丢失整批记录的异步队列。独立 CLI 使用仍可按次打开关闭；停止服务时释放连接。
4. 基准工具补充每次查询的线程 CPU 时间、进程 RSS、cgroup 限额与内存；新增隔离的真实 REST/MCP 基准，使用独立用户令牌，并校验完整结果哈希与日志条数。

## 已完成：查询层 1 核 / 256 MiB

远端 ARM/Python 3.12/SQLite 3.34.1，当前约 9.4 万条文的隔离文件副本。
通过 systemd cgroup 设置 CPUQuota=100%、MemoryMax=256M、MemorySwapMax=0。
只对隔离副本调用 fadvise(DONTNEED)，使后续缓存页计入测试 cgroup；没有清理线上数据库或全机缓存。
每个并发档 96 次请求，先预热；因此时延是热查询，内存峰值覆盖预热与运行。

| 执行并发 | 基线 QPS | 候选 QPS | 基线查询 CPU ms/次 | 候选查询 CPU ms/次 |
|---:|---:|---:|---:|---:|
| 1 | 14.60 | 17.74 | 67.53 | 55.58 |
| 2 | 13.61 | 16.82 | 73.09 | 59.33 |
| 4 | 12.43 | 15.35 | 80.29 | 64.50 |

cgroup 内存峰值 176.07 → 161.80 MiB；进程峰值 RSS 69.16 → 67.24 MiB。六组结果哈希一致。
原始数据见 `baseline-query-1cpu256m.json` 与 `candidate-query-1cpu256m.json`。
这不是整台 VM 的最低内存承诺，也不包含真实协议、认证、日志和操作系统常驻开销。

## 2 核 / 2GB：重检索执行额度

最终候选增加宽泛子串有序扫描与 REST/MCP 共享执行队列（执行 4，等待 16）。
8 个独立令牌分别建立客户端和 MCP 会话；每协议每并发档持续 60 秒。
CPUQuota=200%、MemoryMax=2G、MemorySwapMax=0，实际限额由脚本读取确认。
CPU 是物理 4 核主机上的平均 2 核配额，没有将进程固定到两个物理核。
基准服务和负载发生器同进程运行，包含客户端 CPU、序列化与结果校验，结果不是线上 SLA。

| 协议/请求并发 | 无执行额度 QPS | 限执行 4 的 QPS | 无额度 P95 ms | 限执行 4 的 P95 ms |
|---|---:|---:|---:|---:|
| REST / 4 | 35.03 | 33.89 | 203.28 | 222.26 |
| REST / 8 | 27.35 | 32.04 | 536.32 | 397.27 |
| MCP / 4 | 36.55 | 37.43 | 212.03 | 207.88 |
| MCP / 8 | 34.28 | 38.54 | 459.81 | 374.89 |

这是同一查询优化代码、有无执行队列的对比，不能当作旧版与新版整体对比。
4 请求档 REST 有约 3% 波动/开销；8 请求档吞吐提高约 17% / 12%，P95 降低约 26% / 18%。
MCP 混合六类搜索及 article/list，REST 仅六类搜索，因此两个协议的 QPS 不能直接横比。
候选合计 8553 条日志（含预热）完整，无请求错误，所有结果哈希一致。
哈希仅排除随日期自然变化的 freshness_days，其他字段不忽略。
进程采样 RSS 峰值约 153.25 MiB，服务阶段 cgroup 采样约 174.06 MiB，包含复制/启动的
cgroup 峰值 398.42 MiB；不能将其中任意数值当作整台 VM 的最低内存。
早期试跑源副本页面缓存归属不同，故不宣称数百 MiB 的内存下降。

默认执行 4 是本轮实测的折中值；可调参数通用于不同部署，不依赖甲骨文接口或 ARM 指令。
更多接入者通过排队复用有限执行额度，不建议把 CPU 密集检索执行数随在线人数等比例提高。

## 16 独立客户端补测与建议

每协议 60 秒，仍为执行 4、等待 16；REST 31.73 QPS、P95 661ms、P99 741ms，
MCP 36.96 QPS、P95 714ms、P99 806ms。4180 条日志完整，无错误，结果校验通过。
进程 RSS 峰值 173.19 MiB，服务阶段 cgroup 采样峰值 193.13 MiB，含启动峰值 398.18 MiB。
原始数据见 candidate-api-16clients-2cpu2g.json。增加客户端没有提高算力，但有界排队避免
无限扩大执行数带来的吞吐下降。此实验仅持续两分钟，不能据此承诺长期 SLA。

企业初始配置建议：单 ASGI worker，执行 4、等待 16，每客户端最多并发 2；2 核/2GB
作为当前资料规模的查询服务起点。按实际查询混合、P95 与 CPU 利用率逐步调节总入口流量，
保留操作系统、代理和维护任务预算。不要按压测极限配置长期流量，也不要将 16 个同时请求
解读为最多只能注册 16 名用户。本轮未直接提高线上 nginx 并发，部署后先观察真实流量。
