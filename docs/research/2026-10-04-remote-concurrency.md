# 远端 CPU 与查询并发研究（2026-10-04）

## 结论

当前部署的搜索链路存在 CPU 容量瓶颈。短时查询层实验中，4 个线程已使用约 3.27 核；增加到 8 个线程，吞吐基本不变，P95 延迟明显增长。首要优化是减少查询 CPU 开销，尤其是修订版本判断里的重复全表扫描，而不是直接增加 ASGI worker 或提高 nginx 限额。

本次只读检查生产配置、聚合查询日志，并运行有限的只读查询实验。没有修改生产数据库、服务、令牌或 nginx；索引实验只在进程内的 SQLite 内存副本执行，进程退出即销毁。此文为研究结论，不是已上线优化记录。

## 实际部署与边界

- Oracle ARM，4 核，内存约 22.4 GiB，可用约 20.8 GiB；无 swap 使用。
- 检查时 load average 为 0，没有观察到持续 CPU 饱和；systemd 未设置 CPU 配额或核绑定。
- 服务版本 0.7.2，Python 3.12，SQLite 3.34.1，MCP SDK 2.2.0。
- 单个 `chinalaw-server serve --server` 进程；库文件约 339 MiB，修订表 2586 行。
- nginx 每令牌 5 请求/秒、burst 20，全局查询连接上限 8。闲置 MCP SSE GET 不计入查询配额。
- MCP SDK 的同步工具调用已通过 `anyio.to_thread.run_sync` 分派；REST 同步路由也在线程池执行。SQLite 查询可释放 GIL，因此单 ASGI worker 不等于只能使用一个 CPU 核。
- 服务还包含单例维护 worker、进程租约、进程内维护协调与 MCP 会话状态。直接改成多 worker 不是可行的现成配置方案。

## 原查询链路的短时并发实验

在远端独立低优先级进程内调用 `catalog.search_library`，数据库以只读方式连接；查询集为“保证期间”“合同”“的”“连带责任保证”“民法典第五百零四条”“股东抽逃出资责任”，公开库、默认全部类型、limit=10。每档 24 次调用，线程数 1/2/4/8；每次调用独立连接。CPU 核数为进程 CPU 时间除以墙钟时间。

| 同时执行线程数 | 吞吐（查询/秒） | 平均使用核数 | P50 ms | P95 ms |
|---:|---:|---:|---:|---:|
| 1 | 6.40 | 0.99 | 163 | 292 |
| 2 | 10.96 | 1.89 | 191 | 336 |
| 4 | 17.20 | 3.27 | 215 | 442 |
| 8 | 17.27 | 3.48 | 377 | 1005 |

这是小样本、热缓存的查询层实验，不包含认证、日志写入、MCP/REST 编解码、nginx 与公网 RTT，也不代表稳定生产 QPS 或用户数。P95 只有很少尾部样本。它足以说明原链路提高执行并发到 8 后已难以增加吞吐，但不足以定出上线限额。

## 已定位的 CPU 热点

### 1. 修订表缺索引：优先修复

调用链：`search → _rank_and_fold → _law_search_context → _work_version_starts → _fetch_revisions`。

生产 `revisions` 仅有主键索引；实际 `EXPLAIN QUERY PLAN` 显示按 `law_id` 查修订走 `SCAN TABLE revisions`，完整修订查询还使用临时 B-tree 排序。

带 cProfile 的单次“合同”查询耗时约 222ms，其中 `_fetch_revisions` 调用 62 次、累计约 164ms；整个查询执行 SQL 296 次。“保证期间”约 72ms，其中版本开始日期计算约 45ms。单次墙钟耗时与 CPU 时间基本一致。

建议通过正式 schema migration 增加 `revisions(law_id, effective_at)` 索引，并同步更新新库 schema。在搜索版本判断里只读取施行日期，避免调用读取完整修订、排序的接口；进一步批量读取候选作品的版本元数据，消除逐法规往返。

不要简单删除历史版本判断：施行日期、修正关系、历史时点和版本折叠影响法律检索正确性。

### 2. 搜索与近似补充

“的”等单字查询无法获得二元组索引收益；广泛匹配仍要扫描/排序。“股东抽逃出资责任”等查询主要耗时于近似召回，最多取 500 个候选并逐条进行 Unicode 归一化与片段验证。

后续措施：将固定归一化工作移至入库或按内容哈希缓存；评估 FTS 排序和候选获取策略；对短词、广泛匹配和近似搜索设置独立执行预算与超时。减少候选不能直接作为无损优化，必须验证召回、排名、同条共现和版本折叠。

## 索引隔离实验

用 SQLite backup API 将生产库复制进内存，只对内存副本增加实验索引。所有六类查询、每类三次的结果与同一副本加索引前逐对象比较一致。

| 查询 | 副本原逻辑中位数 ms | 副本仅加索引 ms | 耗时降低 |
|---|---:|---:|---:|
| 保证期间 | 32.1 | 22.9 | 29% |
| 合同 | 88.8 | 49.7 | 44% |
| 的 | 171.0 | 131.7 | 23% |
| 连带责任保证 | 30.5 | 22.7 | 26% |
| 民法典第五百零四条 | 143.1 | 137.1 | 4% |
| 股东抽逃出资责任 | 106.5 | 97.1 | 9% |

同一内存副本单线程混合吞吐由 10.4 增至 13.0 次/秒，约提升 25%。100 个修订日期查询的微基准由 60.22ms 降至 0.31ms，计划变为 covering index lookup；该微基准提升不能当成整个服务的提升。

另测只改为读取日期、不加索引：生产只读库上的“合同”仍约 195ms，收益很小，说明仅减少返回列无法解决全表扫描。

内存副本用了 SQLite shared cache，多线程测试出现明显串行化，与生产独立文件连接条件不同，因此不使用其并发数据预测生产容量。要取得可信的索引后并发收益，应在独立文件快照上使用与生产相同连接模式重测。

## 优化实施顺序

1. **先补修订索引并精简版本日期查询。** 做 schema migration、升级与回滚验证；覆盖当前/历史效力、修正关系、旧 ID 与版本折叠的一致性测试。索引构建安排在备份后的维护窗口执行。
2. **缓存重复计算。** 优先缓存版本元数据，其次是热点查询结果，并合并同时到达的相同查询。缓存键包含数据世代、公开/私域权限、全部过滤参数、实际解析后的北京时间日期和检索算法版本；导入、修订、删除、恢复后失效，鉴权仍每次执行。避免用只含 query 的共享缓存。
3. **控制重查询实际执行数。** 先比较 3–4 个搜索执行槽与现有方式，使用有界短队列；法条直读、轻量解析和 MCP 握手避免被慢搜索占满。不能直接把整个线程池压到 4，因为管理功能也使用线程池。HTTP 并发、查询执行槽与用户人数是不同指标。
4. **验证后再调整 nginx。** 保留每令牌公平限制；只有应用层有队列、超时和退避语义，且端到端容量测试通过后，才试验将入口并发从 8 调至 12/16。入口放宽本身不增加 CPU 容量。
5. **优化后再判断是否扩容。** 若 Python 运算成为主因，可拆独立查询进程池；若需要多个 API 实例，先将维护任务单例化、处理跨进程维护协调和 MCP 会话路由。当前 SQLite 计算已经能利用多个核，单纯多 worker 不能凭空增加 4 核总算力。
6. **最后核验其他开销。** 鉴权会更新 token 的 `last_used_at`，查询日志逐条打开 SQLite 并写入；优化搜索后需检查它们是否变成写锁/提交瓶颈。可评估时间粒度合并更新、WAL 与日志批写，明确掉电丢日志边界；本次未实测它们的端到端占比。

## 第二轮：减少正文扫描与重复匹配的 CPU 开销

最终保留两项通用优化，仍使用 schema v17，不改变切词或检索协议：

- 对纯汉字/数字的子串条件直接检查正文和标题，不再对每条文本调用 SQLite `lower()`。
  ASCII 及其他 Unicode 字母仍使用原来的大小写处理，混合输入逐条件判断。
- 在单批近似候选中，按原始正文复用片段匹配结果，包括匹配失败；不同版本经常有
  相同正文。缓存最多随候选池保存 500 个文本键，查询结束即释放，既不跨请求也不
  跨权限共享。每条结果仍独立构建来源、条号等字段，并复制匹配片段列表，避免引用共享。
  被淘汰的候选不再预先构建结果字典。
