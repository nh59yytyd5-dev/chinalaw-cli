# 模糊搜索设计方案（草案）

> 状态：部分被取代。全文近似匹配（4.1–4.3、4.7 节）按 58 部法规设计，已由
> `2026-09-24-fulltext-search-at-scale.md` 取代；保留与作废清单见该文第 2.4 节。
> 分支 `feat/fuzzy-search`，日期 2026-09-23。
> 本文按 `docs/CONTRACT.md` §9 的要求整理 Context / Decision / Consequences /
> Alternatives / Follow-ups，确认后可作为 `protocol-change` issue 正文。

## 1. 背景

### 1.1 现状

- **全文检索**（`search`）：按空白拆词，每个词必须在条文里原样、连续出现。
  所有词都不少于 3 个字时走 FTS5 trigram 短语匹配；任一词少于 3 个字时，整句退回
  `LIKE` 子串匹配。
- **法规名解析**（`resolve`、`article`、`articles`、`--in` 等共用）：依次尝试
  id、全称、短称、精确别名、派生别名，最后用 `LIKE` 子串兜底（`like_fallback`）。
  2–4 字、以“法”等结尾的短名不走兜底，防止“合同法”落到“劳动合同法”。
- 远端 MCP HTTP 的 `chinalaw_article` 在法规名解析失败时只返回
  `article_not_found`，没有任何诊断或候选。

### 1.2 实测缺口

本机资料库 58 部法规、8083 条条文，逐条实测：

| 类型 | 查询 | 现状 | 原型结果 |
| --- | --- | --- | --- |
| 长句不连续 | 用人单位未与劳动者订立书面劳动合同 | 0 条 | 劳动合同法第八十二条排第一 |
| 长句不连续 | 显失公平撤销 | 0 条 | 民法典第一百五十一条等进入前三 |
| 长句不连续 | 约定的违约金超过造成的损失 | 0 条 | 商品房买卖合同纠纷解释第十二条、合同编通则解释第六十五条排前二 |
| 词中夹字 | 二倍工资 | 0 条 | 找到“二倍的工资” |
| 标点 | 违约金，过高 | 0 条 | 拆成两个片段后可命中 |
| 数字写法 | 劳动者提前30日书面通知解除劳动合同 | 0 条 | 改写为“三十日”后劳动合同法第三十七条排第一 |
| 错别字 | 表现代理、诉讼实效、格式条目、连代责任、善意去得 | 0 条 | 提示表见代理、诉讼时效、格式条款、连带责任、善意取得 |
| 法规简称 | 个保法、电商法、消保法、治安处罚法 | 解析失败 | 正确法规均排第一候选 |
| 法规名变体 | 民事诉讼法司法解释、劳动争议司法解释（一）、合同编通则司法解释 | 解析失败 | 正确法规均排第一候选 |
| 学理术语 | 不安抗辩权、情势变更、买卖不破租赁、加速到期 | 0 条 | 无解，见第 9 节 |

学理术语单独统计：30 个常用术语中，24 个在条文原文里一次都不出现。这一类不是
“模糊”问题，而是术语与法条用语之间的映射问题。

原型还暴露了一个必须正视的风险：“合同法”的第一候选是“劳动合同法”，相似度接近
满分。库里没有已废止的合同法，任何自动采用都会引错法。“婚姻法解释”的第一候选是
婚姻家庭编解释（一），两者有承继关系，但不是同一份文件。

## 2. 目标与不做的事

本期目标：

1. **全文容错**：长句不连续、词中夹字、标点、全半角、阿拉伯数字写法都能召回。
2. **错别字提示**：查询词在资料库里根本不存在时，给出语料中真实出现的相近词。
3. **法规名候选**：法规名解析失败时，返回按相似度排序的候选，不自动采用。

本期不做：

- 学理术语映射，另行决策，见第 9 节。
- 拼音、首字母检索，繁体转简体。
- 改变精确检索的现有行为，或移除现有的 `like_fallback`。
- 新增第三方依赖、改动数据库 schema、新建索引。

## 3. 已确认的决策

| 编号 | 决策 | 依据 |
| --- | --- | --- |
| D1 | 本期覆盖全文容错、法规名候选、错别字提示 | 2026-09-23 对齐 |
| D2 | 精确检索照旧排在前面；某类命中少于 5 条时，自动追加近似结果并逐条标注 | 2026-09-23 对齐 |
| D3 | 法规名的近似结果只作为候选返回，不用于取条 | 2026-09-23 对齐；“合同法”反例 |
| D4 | 面板只改全文检索页 | 2026-09-23 对齐 |
| D5 | 近似匹配只放宽“连续出现”，不改字；改字只出现在“你是不是要找”里，且不自动执行 | 本方案提出 |

D5 是整套设计的安全底线。唯一的例外是确定性的等价改写：全角转半角、阿拉伯数字转
中文数字。这两种改写不涉及猜测。

## 4. 详细设计

### 4.1 查询归一化

只作用于近似检索，精确检索的输入保持原样。

- 全角字母数字转半角，全角空格视为空白。
- 空白与常见标点都作为片段分隔符：`，。、；：！？（）《》〈〉【】〔〕「」『』“”‘’…—·/`
  及其半角形式。连字符、小数点、百分号不作分隔符。
- 数字生成等价变体，与原写法并存：`30日` 对应 `三十日`，`30%` 对应 `百分之三十`，
  `2023年` 对应 `二〇二三年`。超过 9999 的数字和小数不改写。
- 单字片段不参与近似打分。
- 近似检索只看归一化后的前 80 个字，防止整段粘贴拖慢查询。

### 4.2 全文近似匹配

适用于公开条文；私域条款用同一机制，但只在调用方有私域权限时运行。

**候选召回**，一次查询只走一条路径：

- 片段拆成的不重复二元组不超过 24 个时，全表扫描一次，保留至少含一半二元组的条文。
  这条路径能处理“二倍工资”这类被插字打断的短词。
- 超过 24 个时（通常是整句粘贴），用现有 trigram 索引做 OR 查询，按 bm25 取前 500 条。
  结果为空时退回前一条路径。
- 两条路径都遵守 `--in` 与 `--in-part` 过滤。

**打分**，逐条候选计算：

1. 每个片段从左到右贪心拆成在条文中出现过的最长子串，每段至少 2 个字。
2. 这些子串必须落在同一个窗口里。4 字及以下的片段，窗口长度为片段长度加 2，只容许
   中间夹一两个字，例如“二倍的工资”。更长的片段，窗口长度取片段长度的两倍与片段长度
   加 40 两者中的较大值，大致对应同一句话的范围。
3. 覆盖率等于窗口内命中的字数除以全部片段的字数。

**接受条件**：覆盖率不低于 2/3，并且最长子串至少 3 个字，或者至少有 2 段子串。
这条规则让“违约今”不会召回所有含“违约”的条文，也让“表现代理”不会召回相隔很远的
“表现”和“代理”。“订金”这类两字词不会被扩展成“定金”，因为近似匹配不改字。

**排序**：覆盖率高者在前，其次是命中范围更紧凑的，其次是现行有效的法规，其次是更
短的条文、更新的法规、条文顺序。

**合并**：精确命中保持原有顺序排在前面，近似命中按 id 去重后追加，总数不超过
`--limit`。触发条件按命中类型分别判断：该类精确命中数少于 `min(5, limit)` 时才补充。

**阈值说明**：2/3、窗口长度、24 个二元组、500 条等数值是初值。实施时用第 7 节的
回归查询集校准，校准结果写回本文。

### 4.3 错别字提示

- 只在近似检索被触发时运行，只检查 3–8 个字、在公开条文中一次都不出现的片段。
  判断“是否出现”用现有 FTS 索引，开销很小。
- 为每个片段生成编辑距离为 1 的模式：替换一个字、多一个字、少一个字、相邻两字互换。
  全表扫描一次，提取实际出现的字符串并计数，排除含标点的结果。
- 出现至少 2 次才提示，每个片段最多提示 3 个，按出现次数排序。
- 两字词不提示，歧义太大，例如定金和订金都是合法用语。
- 只提示，不替换，也不自动用建议词检索。输出附带可直接执行的检索命令。
- 私域条款的用语只在调用方有私域权限时参与提示，避免私域词汇外泄。

原型结果：表现代理提示表见代理，出现 3 次；诉讼实效提示诉讼时效，出现 81 次；
格式条目提示格式条款，出现 33 次；定金、订金都在语料中存在，不触发提示。

### 4.4 法规名候选

**比较前的归一化**，只用于打分，不改变任何存储数据：

- 去掉“中华人民共和国”“最高人民法院”“最高人民检察院”前缀，去掉“关于”“适用”
  “若干问题”“的”、书名号和括号，“司法解释”视同“解释”。
- 查询中的四位年份（19xx、20xx）提取为版本提示，不参与名称比较。

**打分**：每部法规取全称、短称、别名、派生别名，逐一与查询比较，取最高分。

- 主体是最长公共子序列：查询有多少字按顺序出现在名称里，名称有多少字被查询覆盖，
  两者加权。查询是名称的子序列时加分，这对应“个保法”“电商法”这类缩写。
- 再叠加最长连续公共子串，奖励连续命中的名称。原型只用公共子序列时，“民法点”与
  民事诉讼法的别名“民诉法”同分；叠加这个信号后，民法典以 0.667 对 0.6 排在前面。
  各信号的权重用回归查询集校准。

**排序与收敛**：分数高者在前；分数相同时，年份提示匹配的版本在前，其次是现行有效、
有条文、发布更新的。同名多版本只保留排序最前的一个；查询带年份时优先保留对应版本。
分数低于 0.5 的不返回，最多返回 5 个。

**接入点**，全部只在解析失败时出现：

| 入口 | 新增内容 |
| --- | --- |
| `resolve` 未命中 | `candidates` |
| `article` 的 `law_missing` 诊断 | `candidate_laws`、`suggested_candidate_articles` |
| `articles` 的 `law_not_found` | `candidate_laws` |
| `search --in` 的未解析项 | `law_filter.unresolved_candidates` |
| `search --kind law/all` 法规命中不足 | 近似法规命中，逐条标注 |
| MCP HTTP `chinalaw_article` 未命中 | `candidate_laws` |

诊断文字明确写出“候选未自动采用”，并提示候选可能都不对，此时应走 `fetch --list-matches`。
现有的精确解析路径和 `like_fallback` 行为不变。私域规范名称的近似命中使用同一套打分，
只在调用方有私域权限时运行。

原型结果：个保法、电商法、消保法、治安处罚法、民事诉讼法司法解释、劳动争议司法解释（一）、
合同编通则司法解释的正确法规均排第一候选。“担保解释”同时返回担保制度解释和已废止的担保法
解释，候选里会带出效力状态。

### 4.5 输出契约

`search` 新增字段：

```jsonc
{
  "strategy": "fts5|like|empty",      // 不变，仍描述精确检索
  "fuzzy": {
    "applied": true,                  // 本次是否运行了近似补充
    "min_exact_hits": 5,
    "segments": ["用人单位未与劳动者订立书面劳动合同"],
    "counts": {"article": 4, "law": 0, "norm_clause": 0, "norm_source": 0}
  },
  "term_suggestions": [
    {
      "term": "表现代理",
      "suggestion": "表见代理",
      "occurrences": 3,
      "command": "chinalaw search 表见代理 --kind article --format json"
    }
  ],
  "article_hits": [
    {"...": "...", "match_mode": "exact"},
    {
      "...": "...",
      "match_mode": "fuzzy",
      "fuzzy": {
        "coverage": 1.0,
        "matched": ["用人单位", "未与劳动者订立书面劳动合同"],
        "missing": []
      }
    }
  ],
  "law_hits": [
    {"...": "...", "match_mode": "fuzzy", "fuzzy": {"score": 0.93, "matched_name": "个人信息保护法"}}
  ]
}
```

`resolve` 未命中：

```jsonc
{
  "input": "个保法",
  "matched": false,
  "via": null,
  "candidates": [
    {
      "id": "ff8081817b6472a3017b656cc2040044",
      "official_title": "中华人民共和国个人信息保护法",
      "short_title": "个人信息保护法",
      "status": "current",
      "level": "law",
      "score": 0.93,
      "matched_name": "个人信息保护法"
    }
  ]
}
```

`article` / `articles` 未命中的 `candidate_laws` 与上面的候选结构相同。
`suggested_candidate_articles` 沿用现有 `suggested_sibling_articles` 的命名和格式。

兼容性：

- 只新增字段，符合 CONTRACT §1“新增字段不算 breaking”。
- `strategy` 取值、退出码、既有字段含义都不变。`resolve` 与 `article` 未命中仍返回 1。
- `counts` 仍等于各命中列表的长度，因此会包含近似命中；近似命中数单独放在 `fuzzy.counts`。
- 既有的 `match_kind`（primary / relevant）保留。新字段 `match_mode` 表示命中来源，
  两者含义不同，文档中写清楚。
- 示例中的 id 取自本机资料库，分数为示意，以实现为准。

Markdown 输出：近似命中在标题后标“近似”，并列出命中和缺失的片段；有近似补充时在
结果前加一行说明；“你是不是要找”单独成行；`resolve` 与 `article` 未命中时列出候选。

### 4.6 各入口

- CLI 的 `search`、`resolve`、`article`、`articles` 都经过 service 层，自动生效。
- stdio MCP 与 MCP HTTP 的同名工具透传 service 结果；MCP HTTP 的 `chinalaw_article`
  补上未命中候选。REST `/search` 透传。
- 面板全文检索页：近似结果显示“近似”标记和命中、缺失片段；“你是不是要找”显示为可
  点击的检索词；有近似补充时显示一行说明。面板其他搜索框不变。
- `metadata.py` 中面向 agent 的工具说明、`chinalaw-searching` 与 `chinalaw-using` 两份
  skill 及其 `.agents` 副本同步更新。现有 skill 表格称“担保解释”可解析到担保制度解释，
  实测不成立，借此一并更正。

### 4.7 性能与数据边界

原型在 8083 条条文上的耗时：

| 环节 | 耗时 |
| --- | --- |
| 全文近似检索 | 约 10–60 ms |
| 错别字提示，每个片段 | 约 25–45 ms |
| 法规名候选，58 部法规 | 约 1–2 ms |

- 近似路径只在精确命中不足时运行，高频的正常查询不增加开销。
- 开销与条文数大致成线性关系。资料库扩大十倍时，近似路径预计在数百毫秒以内，实施时
  用放大的测试库实测确认。
- 上限：近似输入 80 个字，扫描路径 24 个二元组，索引路径 500 条候选，每次查询最多检查
  3 个错别字片段。服务端现有的 200 字查询上限不变。
- 私域规范：近似检索与错别字提示都只在调用方有私域权限时使用私域数据，与现有
  `include_norm` 边界一致。

## 5. 影响

- agent 以前拿到空结果的查询，现在可能拿到标为 `fuzzy` 的结果。只看 `counts.total`
  判断“是否找到”的调用方需要改为同时看 `match_mode`。skill 与工具说明会强调这一点。
- 带标点的查询即使每个词都出现，也会以近似结果返回，因为精确检索保持原样。这是为了
  不改变精确检索的契约，代价是标注略显保守。
- grounding snapshot 会记录近似命中及其标注，审计时可以区分。
- 精确检索结果不变，现有测试不受影响。

## 6. 备选方案

| 方案 | 结论 |
| --- | --- |
| 默认关闭、显式 `--fuzzy` 才启用 | 不采用。现有 agent 与远端 MCP 客户端不会自动受益 |
| 精确与近似统一打分混排 | 不采用。精确命中会被近似结果稀释 |
| 引入 jieba 分词或更换 FTS tokenizer | 不采用。需要第三方依赖，且会改变精确检索行为；本场景用二元组覆盖率即可 |
| 法规名高置信时自动采用 | 不采用。“合同法”反例说明阈值挡不住 |
| SQLite spellfix1 扩展 | 不采用。标准库自带的 SQLite 通常不含该扩展 |
| 学理术语交给近似匹配 | 做不到。术语本身不在条文里，见第 9 节 |

## 7. 测试计划

- **单元测试**：归一化与数字变体；接受与拒绝的典型例子，包括二倍工资、显失公平撤销
  应命中，违约今、表现代理不应召回无关条文；错别字提示；法规名候选排序、年份提示、
  多版本收敛。
- **行为测试**：精确命中达到 5 条时不运行近似；`--limit` 与 `--in`、`--in-part` 在近似
  路径同样生效；无私域权限时既不返回私域近似命中，也不返回私域用语提示；“合同法”
  仍然解析失败，劳动合同法只出现在候选里。
- **契约测试**：新增 JSON 字段、Markdown 渲染、stdio MCP、MCP HTTP、REST。
- **回归查询集**：把第 1.2 节的查询和常见 agent 查询整理成基于仓库 fixture 的测试，
  锁定期望的首位结果，作为阈值校准依据。
- **面板**：Playwright 验收全文检索页的近似标记与“你是不是要找”。
- **性能**：用放大的测试库检查近似路径耗时，只设宽松上限，避免测试不稳定。

## 8. 实施步骤

1. 纯函数模块：归一化、片段打分、法规名相似度、错别字模式生成，附单元测试。
2. service 层接入：全文近似补充、错别字提示、各入口的法规名候选、MCP HTTP 未命中。
3. Markdown 输出、`metadata.py`、CONTRACT、ARCHITECTURE、skills、CHANGELOG。
4. 面板全文检索页、前端构建产物、Playwright 验收。

## 9. 学理术语：神经网络方案评估

问题：不安抗辩权、情势变更、买卖不破租赁这类术语不在条文原文里，近似匹配无从下手。
可选方向有三类。

### 9.1 向量语义检索

用中文向量模型把条文和查询编码成向量，按语义相近程度召回。

优点：

- 不需要人工整理词表。
- 能处理口语和整句提问，例如“被公司辞退有没有补偿”“精神损失费”。

对本项目的问题：

- **依赖**：需要推理运行时和模型文件，小模型约百兆级，大模型可达 GB 级。这与“CLI
  核心无第三方依赖”冲突，只能做成可选安装项。
- **永远有结果**：向量检索总能返回“最像的”条文，与“缺失即报错”的底线相冲突，
  必须配合阈值与醒目标注。
- **近义概念混淆**：定金与订金、撤销与撤回、抵押与质押在向量空间里往往很近，
  而法律上是不同概念。
- **不可解释**：无法说明为什么命中，不符合“人可复核”的原则。
- **维护成本**：每次入库或修订都要重算向量；更换模型会改变结果，影响 grounding
  snapshot 的可复现性。
- **效果未经验证**：从学理术语找法条是公认的难任务，通用模型的效果需要先用评测集量出来。

对开源项目而言，这条路适合做成默认关闭的可选安装项，结果标为 `semantic`，只作为
召回线索。自托管服务器的硬件足以运行中小模型，但不能假设每个用户都有这样的环境。

### 9.2 大模型离线生成、人工审核的术语表

用大模型离线为资料库起草“术语到法条用语、相关条文”的映射，人在面板里逐条审核，
审核通过的映射作为数据入库或随仓库发布。检索时按映射做确定性的查询扩展，命中标注
“术语映射”并附映射来源。

优点：

- 可解释、可复核、结果确定，运行时零依赖，符合项目原则。
- 神经网络用在它最擅长的环节：批量起草。人负责它最不可靠的环节：法律准确性。
- 仓库已有先例：`alias_agent` 通过标准库调用兼容 OpenAI 接口的模型，按环境变量开启。
- 公开的术语表可以像 fixture 一样随仓库发布，社区通过 PR 补充。

缺点：

- 覆盖范围取决于审核进度。
- 法规修订后条号会变，映射要以法条用语为主、条号为辅，并绑定版本。
- 需要新的数据格式，属于协议变更，要单独做设计记录。

### 9.3 让调用方 agent 自己改写查询

调用方本身就是大模型，熟悉学理术语。检索完全落空时，返回结构化提示：“法条原文通常
不使用学理术语或俗称，请改用法条表述检索，并用 `article` 核对。”同时在 skill 里写明
这一做法。

优点是几乎零成本，可以立即上线。缺点是帮不了面板上的人工检索，效果取决于 agent 的能力。

### 9.4 建议

1. **本期顺带做 9.3。** 只加一条提示和一段 skill 说明，工作量很小。
2. **下一期做 9.2。** 这是术语问题的正解，也是神经网络在本项目里最合适的用法：
   离线起草，人工把关。
3. **9.1 先评测再决定。** 用一组真实查询和期望条文比较三种做法的召回率。只有明显优于
   “近似匹配加术语表”时，才以可选安装项的形式提供。

结论：值得用神经网络，但建议用在离线起草术语表上，而不是放进每次检索的运行时。
