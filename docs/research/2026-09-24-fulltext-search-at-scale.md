## 0. 结论

- **第一阶段不引入任何新服务，也不引入新依赖。** 条文索引从 trigram 换成“Python
  预切二元组 + FTS5 contentless 表”，查询改成两条通道：精确短语通道保证现有精确
  能力不退化，排序召回通道解决长句和口语查询。原型在 70 万条真实条文上验证：需求中
  两个 0 命中的例子都排第 1，FTS 召回 3–75ms，索引 383MB，全量重建不到 1 分钟。
- **语义召回暂时搁置。** 口语和学理术语先靠调用方 agent 改写查询，以及人工审核的
  术语表解决（第 7 节）。
- **效力状态（status）需要单独治理。** 现在 status 是入库时的快照，会过期，而且现有
  增量同步覆盖不到“旧法被废止”这类变化。多数状态变化发生在事先已知的施行日，可以
  按日历精确处理，其余的靠低频全量对账兜底，见第 6 节。
- **需要引入“法规作品”概念。** 同一部法规的各个版本在 flk 上是各自独立的记录。
  版本折叠和按案件时间取版本（`--as-of`）都依赖把它们归为同一部法规。现有 `--as-of`
  在这一点上已经有缺陷，见第 4.6 节。
- 仍需确认的问题见第 12 节。

### 0.1 已确认的决策（2026-09-24）

| 编号 | 决策 |
| --- | --- |
| E1 | 地方性法规全部入库，默认检索时降权 |
| E2 | 默认行为按合理的方式设计，不要求检索结果与现在完全一致；调用方式和既有字段保持兼容 |
| E3 | 同一部法规的历史版本默认折叠 |

| E6 | 状态对账的时机需要结合施行日期研究，并评估对 flk 的访问压力（第 6 节） |
| E7 | 旧草案的错别字提示、法规名候选作为参考纳入（第 4.5 节） |

## 1. 背景修正：根因不是分词器不支持中文

需求说明里写的根因是“FTS5 默认分词器不适配中文，整句成一个 token”。实际情况是：
`articles_fts` 用的是 `trigram` 分词器，本身支持中文子串匹配。0 命中的原因在查询
构造：`_to_fts_query` 按空格拆词后，把每个词作为短语用 AND 连接，要求每个词在条文
里**原样连续**出现（`service.py:518`）。

| 查询 | 目标条文原文 | 失败原因 |
| --- | --- | --- |
| 法定代表人越权担保 相对人善意 | 担保制度解释第七条：“法定代表人……**超越权限**……订立担保合同……相对人善意的” | “法定代表人越权担保”在原文中不连续 |
| 公司为他人提供担保 董事会 股东会决议 | 公司法第十五条：“公司向其他企业投资或者**为他人提供担保**……由董事会或者股东会决议” | “公司为他人提供担保”在原文中不连续 |
| 担保 | — | 2 个字，达不到 trigram 的 3 字下限，退回 LIKE 全表扫描 |

这个区别影响方案选择：问题不在“切不开”，而在“只做短语全匹配、不做相关度排序”。
另外，“越权”只是“超越权限”的子串。词典分词（jieba 等）会把原文切成“超越/权限”，
查询里的“越权”反而匹配不上；二元组切分没有这个问题。

## 2. 规模与数据

### 2.1 数据规模（实测）

用 Hugging Face 数据集 `senry5433/china-effective-laws-regulations`（flk“有效及
尚未生效”口径，快照 2026-08-26）统计：

| 类别 | 法规数 | 条文数 | 字数 |
| --- | ---: | ---: | ---: |
| 法律 | 483 | 37,250 | 438 万 |
| 行政法规 | 589 | 23,309 | 283 万 |
| 司法解释 | 362 | 9,071 | 124 万 |
| 监察法规 | 2 | 347 | 6 万 |
| 地方性法规 | 15,134 | 633,295 | 8,344 万 |
| 合计 | 17,701 | 703,272 | 9,195 万 |

- 平均每条约 130 字。全国层级（前四类）合计约 7 万条，**地方性法规占 90%**。
- 加上已废止、已修改的历史版本（flk 全量约 2.2–3 万部），条文总量预计在 100 万条
  上下。本文按 100 万条、1.2 亿字设计。
- **flk 不收录部门规章。** flk 的分类只有宪法、法律、行政法规、监察法规、地方性法规、
  司法解释。部门规章要从国家规章库（gov.cn）获取，来源调研见附录 A。这是数据范围
  问题，不影响检索设计。

### 2.2 第三方数据集只能作正文来源，不能作状态来源

上述数据集把合同法、担保法、民法总则、民法通则都标为“有效”（实际已于 2021-01-01
废止），公司法 2013、2018、2023 三个版本也全部标为“有效”。**效力状态必须以 flk
官方元数据为准。** 批量导入时，第三方快照只能用来加速拿到正文，状态和版本关系要以
flk 接口为准重新核对。

### 2.3 现有实现在百万级下的问题

| 问题 | 现状 | 放大后 |
| --- | --- | --- |
| LIKE 兜底 | 2 字查询走 `LIKE` 全表扫描 | 70 万条上每次约 195ms，而且没有相关度排序 |
| 索引体积 | trigram 索引约为正文的 4 倍，FTS 表还存了一份正文副本 | 仅条文索引就会超过 1GB |
| 排序 | 只按 bm25 排序 | “经济补偿”精确命中 490 条，前 10 条中 9 条是地方性法规 |
| 历史版本 | `revisions.snapshot_json` 再存一份全文 | 历史版本多时体积成倍增加 |
| 备份 | zip 包上限 512MiB，展开后上限 2GiB，文件数上限 2 万（`admin/backups.py:36`） | 全量入库后会触发 `backup_too_large` |
| 法规名解析 | 58 部法规几乎没有重名 | 上千部“××省物业管理条例”一类同名地方法规，`like_fallback` 误命中风险显著上升 |

## 3. 原型实测

原型位于 `/tmp/flkproto`，没有改动仓库代码。语料为上述 70 万条条文，测试机为 Mac
（Apple Silicon）。**甲骨文 4 核 Ampere 预计慢 2–3 倍**，实施前要在服务器上复测。

### 3.1 三种索引方案

| 方案 | 索引体积（contentless，不含正文） | 建库耗时 |
| --- | ---: | ---: |
| T：trigram（现状） | 534MB | 34s |
| **B：Python 预切二元组 + unicode61** | **383MB** | **27s** |
| J：jieba 搜索模式分词 + unicode61 | 243MB | 32s（8 进程） |

正文表本身约 383MB。三种方案全量重建都在 1 分钟以内。

### 3.2 检索质量

排序方法：FTS5 按 OR 召回前 1000 条，再按“查询词覆盖率（按 IDF 加权）+ 片段原样
出现加分 + 法规层级先验”重排。表中数字为目标条文的名次，“—”表示前 50 名内没有。

| 查询 | 目标条文 | B 二元组 | J jieba |
| --- | --- | ---: | ---: |
| 法定代表人越权担保 相对人善意 | 担保制度解释第七条 | **1** | 1 |
| 公司为他人提供担保 董事会 股东会决议 | 公司法第十五条 | **1** | 2 |
| 用人单位未与劳动者订立书面劳动合同 | 劳动合同法第八十二条 | 1 | 1 |
| 劳动者提前三十日书面通知解除劳动合同 | 劳动合同法第三十七条 | 1 | 1 |
| 诉讼时效期间为三年 | 民法典第一百八十八条 | 1 | 2 |
| 显失公平撤销 | 民法典第一百五十一条 | 2 | 3 |
| 约定的违约金超过造成的损失 | 民法典第五百八十五条 | 4 | 5 |
| 二倍工资 | 劳动合同法第八十二条 | 8 | 6 |
| 表见代理 | 民法典第一百七十二条 | 21 | 21 |
| 离婚冷静期 | 民法典第一千零七十七条 | 17 | 17 |
| 员工被辞退赔偿 | 劳动合同法第四十七条 | — | — |
| 不安抗辩权 | 民法典第五百二十七条 | — | — |
| 高空抛物 | 民法典第一千二百五十四条 | — | — |

- 用法条原文用语的查询，二元组方案基本进入前 4；jieba 没有更准，重排还慢 5 倍。
- 最后五条是语义和学理术语问题：条文里根本没有这些词（“不安抗辩权”在 70 万条中
  出现 0 次）。任何字面检索都解决不了，处理方式见第 7 节。
- 排名靠前的结果中混有民法通则、民法总则等已废止法律，原因是数据集的 status 错误，
  也说明默认排序必须考虑效力状态。

### 3.3 精确匹配一致性

二元组短语查询（把“表见代理”写成相邻的“表见 见代 代理”）与 `LIKE '%…%'` 对比：

| 查询 | 二元组短语 | LIKE | 说明 |
| --- | ---: | ---: | --- |
| 表见代理 / 善意取得 / 经济补偿 / 超越权限 | 4 / 20 / 490 / 116 | 4 / 20 / 490 / 116 | 完全一致，二元组 1–2ms，LIKE 约 195ms |
| 第五百七十七条 | 5 | 5 | 一致 |
| 30日 | 178 | 1,359 | 中文与数字交界处漏召回，见 4.2 |
| 5%、GB/T | 偏少 | — | 符号不进索引，见 4.2 |

结论：纯中文查询的精确通道可以完全由二元组索引承担，条文表不再需要 trigram 索引。
中文与数字、符号混写的查询，需要“索引召回候选 + 原文子串校验”来保证与 LIKE 一致。

### 3.4 延迟

| 场景 | FTS 召回 | 重排 |
| --- | ---: | ---: |
| 常规查询（2–6 个片段） | 3–75ms | 约 25ms |
| 整段粘贴（69 个二元组） | 199ms | 33ms |
| 全是高频词（“国家 规定 管理 部门”） | 291ms | 25ms |
| 对照：LIKE 全表扫描 | 约 195ms | — |

最坏情况在 ARM 上预计 0.6–0.9 秒，仍在“秒级以内”，但需要 4.3 节的降级策略。

## 4. 第一阶段设计：全文检索

### 4.1 索引结构

- 新建 `articles_bigram_fts`，FTS5 contentless 表（`content=''`），两列：`title`
  （法规标题）、`text`（条文正文），分词器用内置的 `unicode61`。写入内容是 Python
  预先切好、用空格分隔的 token 串。正文只存在 `articles` 表里，不再复制。
- `rowid` 与 `articles.rowid` 一一对应，沿用 `search_indexes.py` 的映射表模式，
  逐部法规增删。
- 删除条文时：SQLite ≥ 3.43 用 `contentless_delete=1` 直接 DELETE；更低的版本用 FTS5
  的 `'delete'` 命令，旧 token 由 `articles.text` 重新计算。切分规则是确定性的，
  所以两种方式等价。
- 下线条文表的 trigram 索引 `articles_fts`（它同时存了一份正文）。`laws_fts` 和私域
  规范的两张 FTS 表数据量小，本期保持 trigram 不动。
- `meta` 记录 `search_tokenizer_version`。版本号变化时，`migrate()` 标记需要重建，
  由显式的 `chinalaw index rebuild` 执行，不在只读路径里偷偷重建。

### 4.2 切分规则

索引与查询共用一个纯函数模块，规则如下：

1. NFKC 归一化，全角转半角，英文转小写。
2. 连续汉字按重叠二元组切分：“超越权限”切成“超越、越权、权限”。只有一个汉字的
   片段保留单字。
3. 连续的数字或英文作为一个 token。
4. 标点、空白处断开，并插入一个边界 token，保证短语匹配不会跨标点。
5. 查询侧附加确定性改写（沿用旧草案 D5）：`30日` 同时生成 `三十日`，`30%` 同时生成
   `百分之三十`。
6. 中文与数字交界处（如“30日”后接“内”），查询边缘的单字 token 改用前缀匹配；精确
   通道的候选一律再用原文子串校验，保证结果与 LIKE 一致。

### 4.3 查询流程

```
查询 ──► ① 引用识别 ──► ② 精确通道 ──► ③ 排序召回通道 ──► ④ 合并、折叠、截断
```

1. **引用识别**。形如“民法典第五百七十七条”“公司法 15 条”的查询，先走现有的法规名
   解析和取条逻辑。命中的条文放在最前面，标注 `match_mode: "citation"`。法规名解析
   失败时不猜，只附候选（旧草案 D3）。
2. **精确通道**，语义与现状相同：按空白和标点拆成片段，每个片段必须原样出现在条文
   中。实现方式为：各片段转成二元组短语后用 AND 连接，再做原文子串校验。2 字的
   查询（如“担保”）也走索引，不再退回 LIKE。只有单字查询仍用 LIKE：单字可能落在
   二元组的后一位，索引无法精确召回；单字查询本身很少见，全表扫描约 0.2–0.5 秒。
   结果标注 `match_mode: "exact"`。
3. **排序召回通道**：
   - 查询全部二元组用 OR 召回。文档频率超过 5% 的高频二元组（如“规定”“人民”）先从
     召回条件中去掉，只参与打分。全部都是高频词时，改为要求所有片段同时出现，避免
     扫描过长的倒排表。
   - bm25 取前 1000 条，在 Python 中重排。分数由 IDF 加权覆盖率、片段原样出现加分、
     命中位置紧凑度、法规层级先验、效力状态先验组成。
   - 覆盖率低于阈值的不返回，防止“只命中一个常见词”的结果。阈值用评测集（第 8 节）
     校准。
   - 结果标注 `match_mode: "ranked"`，附 `matched` 和 `missing` 片段，方便人工复核。
4. **合并**：引用命中、精确命中、排序命中依次排列，按条文 id 去重，总数不超过
   `limit`。同一法规作品的多个版本默认只保留一个，其余折叠为 `other_versions`
   计数，规则见第 4.6 节。
5. **层级降权**（E1）：排序先验中，地方性法规明显低于全国层级。以下情况不降权：
   指定了 `region`；查询中出现省、市名称；全国层级的命中不足 `limit`。

性能上限：查询先截到 200 字（沿用服务端现有上限），召回最多 1000 条，每次查询设
时间预算。超时则只返回精确通道结果，并标注 `degraded: true`。

### 4.4 精确命中的排序也要调整

现在精确命中按 bm25 排序。全量数据下，“经济补偿”的前 10 条中有 9 条是地方性法规。
精确命中的**集合**保持不变，**排序**加入层级与效力先验：法律、司法解释、行政法规
在前，现行有效在前，然后才看 bm25。这会改变现有精确查询的返回顺序，按 E2 接受。

### 4.5 法规名解析在 2 万部规模下的调整

- 派生别名（去掉“中华人民共和国”的短称等）只为全国层级的法规生成。地方性法规必须
  带地名才能精确解析，否则“物业管理条例”会在上百部同名地方法规中随机落点。
- `like_fallback` 命中多部法规时，改为返回候选、不自动采用，与旧草案 D3 一致。
- 法规名候选、错别字提示沿用旧草案的设计。打分改为先用 `laws_fts` 与 `fts5vocab`
  缩小候选范围，不再对所有法规名逐一计算相似度。

### 4.6 法规作品、版本折叠与案件时间

**现有的时间效力功能**都在本仓库里，不只存在于 develop 仓库：

| 入口 | 能力 |
| --- | --- |
| CLI `get` / `article` / `articles --as-of YYYY-MM-DD` | 取某一日期有效的版本 |
| CLI `diff` / `trace --from-as-of --to-as-of` | 比较两个时点的版本 |
| CLI `grounding` / `cite --as-of` | 按事实时点锁定引用 |
| CLI `applicable --date` | 按日期返回时间效力规则线索，规则来自 `data/applicability/` 下 6 份人工整理的文件（民法典、公司法 2023 修订、刑法溯及力等） |
| stdio MCP | `chinalaw_article`、`chinalaw_articles` 支持 `as_of`；有 `chinalaw_applicable` |
| 远端 MCP HTTP | 只有 `chinalaw_article` 支持 `as_of`；没有 `applicable`；`search` 不支持时点 |

**现有缺陷**：`--as-of` 只在**一条 `laws` 记录内部**的 `revisions` 里找版本
（`service.py:1751`）。刑法的 16 个版本存在同一条记录里，所以刑法没问题。民事诉讼法
的 2017、2021、2023 三个版本却是三条独立记录（另有一条重复记录），因此：

```
chinalaw article 民事诉讼法 1 --as-of 2018-01-01
→ version_not_found_as_of（2017 年版明明在库里）
```

flk 上每个版本都是一条独立记录（公司法 2013、2018、2023 是三个不同的 `bbbs`）。
全量导入后，几乎所有法规都会是“多条记录”的形态，`--as-of` 会普遍失效。

**方案**：

- `laws` 增加 `work_id`，把同一部法规的各版本归为一个作品。初值按“标题相同 + 制定
  机关相同”归组；更名的法规（少数）用人工维护的映射表修正。flk 详情的相关资料接口
  （`xgzl`）是否提供历史沿革，实施时核实，若有则优先使用。
- `--as-of` 改为在整个作品的所有版本中，选择施行日期不晚于该日期的最新版本。现有
  “单条记录内的 revisions”继续有效，两种形态统一对待。
- 检索中的版本折叠（E3）：
  - 没有指定时点时，每个作品只显示“今天有效”的版本；没有有效版本的（整部废止），
    显示最后一个版本并标注已废止。
  - `search` 新增可选参数 `as_of`：指定后，每个作品改为显示该日期有效的版本。这就是
    “按案件时间检索”，不需要另做一个功能。
  - 指定 `status=repealed`、`status=amended` 或 `versions=all` 时不折叠。
- `applicable` 规则文件是人工整理的，不随全量数据扩大。本方案不改动它。

## 5. 接口与契约

五个 MCP 工具已有的入参和出参保持不变，只新增可选参数和字段（E2）。

`chinalaw_search` 新增的可选参数：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `mode` | `auto` | `auto`：精确命中在前，排序命中追加在后；`exact`：只跑精确通道，即现有语义；`ranked`：只跑排序召回 |
| `as_of` | 今天 | 按该日期选取每部法规的有效版本，即按案件时间检索（4.6 节） |
| `status` | 不过滤，现行优先 | 例如 `current` 只返回现行有效 |
| `level` | 不过滤 | 例如 `law,judicial_interpretation` |
| `region` | 不过滤 | 地方性法规的地域，例如 `上海市`；指定后地方性法规不降权 |
| `versions` | `folded` | `all` 表示不折叠历史版本 |

每条命中新增的字段：

```jsonc
{
  "match_mode": "citation | exact | ranked",
  "ranked": {"coverage": 0.83, "matched": ["法定代表人", "担保", "相对人善意"], "missing": ["越权"]},
  "work_id": "…",                       // 法规作品，见 4.6 节
  "effective_status_as_of": "current",  // 按 as_of 计算的状态，见 6.3 节
  "status_checked_at": "2026-09-24",    // 最近一次与 flk 对账的日期
  "other_versions": 2
}
```

结果顶层新增 `retrieval: {"mode": "auto", "as_of": "2026-09-25", "degraded": false, "counts_by_mode": {...}}`。
`strategy` 字段保留，取值仍为 `fts5`、`like`、`empty` 之一，含义不变。CLI 的 `search`
与 REST `/search` 同步增加这些参数。远端 MCP HTTP 的 `chinalaw_search` 同步增加
`as_of`，并新增 `chinalaw_applicable`，使远端也能按案件时间检索。

兼容性：按 CONTRACT §0，tokenizer 选择不属于协议；按 §1，新增字段不算 breaking。
行为上的变化有三点，都要写进 CHANGELOG 和工具说明：

1. 以前 0 命中的查询，现在会返回 `ranked` 结果；
2. 精确命中的排序加入了层级与效力先验；
3. 同一法规的历史版本默认折叠。

只看 `counts.total` 判断“有没有找到”的调用方，需要同时看 `match_mode`。

## 6. 效力状态的维护

### 6.1 现状

- `status` 在入库时从 flk 详情的 `sxx` 字段映射而来：1 已废止、2 已修改、3 有效、
  4 尚未生效（`cleaning.py:60`）。之后只有重新同步才会改变。
- 系统不根据日期推算状态：`pending_effective` 的法规过了 `effective_at` 以后，库里
  仍然是“尚未生效”。
- `sync --incremental` 按**公布日期**开窗口（`sync.py:134`）。一部旧法被废止或被修改
  后，flk 上它的 `sxx` 变了，但公布日期还是多年前的，增量同步不会回头检查它。
- 新版本入库时，不会把旧版本改成 `amended`。
- 本地库 58 部法规的 `source_checked_at` 分布在 2026-04-29 至 08-03，最旧的一条已经
  将近 5 个月没有核对。

### 6.2 flk 的状态何时变化（2026-09-24 实测）

| 观察 | 结论 |
| --- | --- |
| 列表接口每条记录都带 `gbrq`（公布日期）、`sxrq`（施行日期）、`sxx`（时效性） | 不必逐条请求详情，一次列表即可拿到全部状态 |
| “尚未生效”共 82 条，施行日期从 2026-09 到 2027-01；没有一条已过施行日期仍标为“尚未生效” | flk 在施行日当天或前后及时切换状态，没有明显滞后 |
| 商标法 2026 修正版（公布 2026-06-26，施行 2027-01-01）标为“尚未生效”；2019 版仍标为“有效”；2013 版标为“已修改” | **旧版本在新版本施行日才变成“已修改”，不是在公布日** |
| 农业法 2026 修订版（施行 2027-01-01）同上，2012 版仍为“有效” | 同上 |
| “修改、废止的决定”作为独立条目出现，`sxx` 为空 | 废止也有自己的公布日和施行日 |
| 列表接口接受 `pageSize=1000`，单次约 1–1.6 秒、415KB | 全部 30,896 条只需 31 次请求 |

由此可以把状态变化分成两类：

| 类别 | 例子 | 能否事先知道 | 处理方式 |
| --- | --- | --- | --- |
| 日历型 | 新法施行：尚未生效 → 有效；新版施行：旧版有效 → 已修改 | 能。公布时就已确定施行日期 | 本地按日期推算，施行日零点起生效，不依赖对账 |
| 事件型 | 废止决定、清理性修改、flk 更正元数据 | 公布时才知道 | 靠对账发现 |

### 6.3 方案

1. **以日期为准推算“某日的状态”**。对任意日期 D（默认今天，按北京时间计算），
   同一法规作品内：
   - 施行日期晚于 D 的版本：尚未生效；
   - 施行日期不晚于 D 的版本中最新的一个：有效；
   - 更早的版本：已修改；
   - 作品已被废止且废止施行日不晚于 D：全部版本为已废止。废止施行日取自 `laws.repealed_at`；
     flk 详情是否直接给出这个日期，还是要从对应的“修改、废止的决定”中读取，实施时核实。

   这就是 4.6 节 `as_of` 用的规则，“今天的状态”只是 `as_of = 今天` 的特例。这样
   日历型变化在施行日零点自动生效，不依赖对账是否按时运行。推算结果放在
   `effective_status_as_of`；flk 给出的原始 `sxx` 仍保留在 `status` 字段中。两者
   不一致时附 `status_conflict` 提示，并以 flk 为准排查。
2. **对账不在仓库里做**：对账和导入都是维护者的数据生产工作，由仓库外的维护脚本
   完成，详见 `2026-09-25-flk-full-import.md` 第 1、5 节。仓库只接收对账结果，
   写入 `status` 与 `status_checked_at`。
3. **施行日复核**由维护脚本完成：对施行日期为昨天或今天的条目，检查 flk 是否已经
   切换状态；没有切换就告警，不改写本地推算。
4. **把“核对时间”交给调用方**：每条命中附 `status_checked_at`；超过 7 天没有核对的，
   附提示“效力状态可能已过期，请以官方来源为准”。

### 6.4 访问压力与 rate limit

- flk 前面有网站卫士 WAF（响应头 `WZWS-RAY`）。没有找到公开的频率阈值。
- 本次调研约 12 次请求，间隔 3 秒左右，全部正常返回 200。
- 每日对账 31 次请求、约 13MB，比一个人在网页上翻几十页还少，触发限流的可能性很低。
- 防护措施：
  - 对账任务的请求间隔固定不低于 3 秒，高于 adapter 默认的 0.2 秒；
  - 串行请求，保留 chinalaw-cli 的 User-Agent 标识；
  - 遇到 WAF 挑战页或非 200 响应立即停止，当天不重试，记录告警；
  - 连续 3 天失败时，在 `doctor` 和面板上显示“状态对账已中断”。
- **真正有压力的是首次全量导入**：约 3 万条记录，每条需要请求详情并下载 docx，合计
  6 万次以上请求，按 3 秒间隔约需 50 小时。这个问题放到批量导入方案里单独解决，
  例如正文先用 CC0 开源快照，flk 只用于核对状态和补齐历史版本。

## 7. 口语与学理术语（语义检索已搁置）

按 E5，本轮不做向量检索。第 3.2 节里字面检索落空的查询（员工被辞退赔偿、不安
抗辩权、高空抛物等）用以下两条路线处理：

1. **调用方 agent 改写查询**：检索没有 `exact` 命中、`ranked` 覆盖率也很低时，返回
   结构化提示：“法条原文通常不使用学理术语或俗称，请改用法条表述检索，并用
   `article` 核对。”同时写进 skill。零成本，随第一阶段上线。
2. **人工审核的术语表**：由大模型离线起草“术语 → 法条用语、相关条文”的映射，人在
   面板里审核后入库。检索时做确定性的查询扩展，命中标注 `match_mode: "term"` 并附
   映射来源。它对面板上的人工检索同样有效。这需要新的数据格式，单独立项。

第 3.5 节的向量实测数据保留，供日后重新评估时参考。

## 8. 评测集与验收

评测集是阈值校准的依据，放在实施的第一步。

- **构成**，约 150 条：
  - 本文与旧草案中的全部实测查询；
  - 按类型补充：法言法语长句、口语提问、学理术语、条号、法规名、错别字、数字写法；
  - 按案件时间的查询：同一问题在不同 `as_of` 下应命中不同版本，例如 2018 年与
    2024 年的公司法担保条款；
  - 从全国层级条文中抽样，由大模型离线生成口语化提问，经人工抽检后，以原条文作为
    期望答案。
- **指标**：
  - Recall@10 与 MRR，按查询类型分别统计；
  - 精确查询零退化：所有现有精确查询，新旧实现返回的命中集合必须一致；
  - 效力正确率：前 10 条中错把已修改、已废止的版本当作现行的比例，目标为 0。
- **性能验收**：在甲骨文服务器上用全量库实测。排序召回 P95 < 1s，精确通道 P95 <
  200ms，全量重建 < 15 分钟。

## 9. 存储与备份

全量约 100 万条时的体积估算：

| 部分 | 体积 |
| --- | ---: |
| 正文与元数据（`articles`、`laws` 等） | 约 550MB |
| 二元组索引 | 约 550MB |
| 历史快照 `revisions.snapshot_json` | 取决于版本数。版本改为独立记录后，快照可以不再保存全文 |
| 合计 | 约 1.1–1.5GB，单文件 |

建议：

- **主库保持单文件**，全文索引放在主库里。服务运行在 WAL 模式下，SQLite 在 WAL 模式
  下不保证跨 ATTACH 多个文件的事务原子性。索引与正文放在同一个文件里，逐部法规的
  增量更新才能与正文写入在同一个事务里完成。
- **在线备份**继续用 SQLite backup API 生成一致快照，但备份包上限要调整：zip 上限从
  512MiB 提到约 4GiB，或改用 zstd 流式压缩。上传恢复路径的上限要同步调整。
- 文件数上限 2 万：如果批量导入为每部法规保存原始文件，就会触到这个上限。是否保留
  原始文件，在批量导入方案里决定。

## 10. 为什么不引入独立服务

| 选项 | 结论 |
| --- | --- |
| Elasticsearch / OpenSearch + IK 分词 | 不采用。JVM 常驻需要 2–4GB 内存；要运维分词插件、集群状态和快照；QPS≈0 的场景用不上它的能力 |
| Meilisearch / Manticore | 不采用。资源占用较小，但多一个服务、多一套备份和数据同步；二元组 FTS5 已经满足延迟要求 |
| PostgreSQL + zhparser | 不采用。需要整体迁移数据库，单文件备份变成 pg_dump |
| SQLite 分词扩展（simple、jieba C 扩展） | 不采用。需要为 ARM 编译并加载扩展；词典分词会漏掉“越权”这类子串；质量不优于二元组 |
| jieba（Python） | 不采用。质量没有优势，重排慢 5 倍，还增加一个依赖 |

重新考虑独立服务的条件：评测显示二元组的召回明显不够，或者服务器实测延迟超过 1 秒
且无法通过降级策略解决。
